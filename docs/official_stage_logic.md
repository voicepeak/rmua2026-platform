# Official stage/route logic (2026-11-06 correction)

This page corrects an error in the earlier local proxy. Do not use the
`1_1 + 2_1` / two-gates-per-segment model for official stage validation.

## Stage logic

Official six stages: `1-3, 3-5, 5-8, 8-12, 12-10, 10-7`.

The course is a shuttle, not one route per stage:

- **Stage 1**: marker 1 -> central hub -> end of route 3. Reaching route 3's
  end triggers stage 2.
- **Stage 2**: return along route 3 to the hub -> route 5. Reaching route 5's
  end triggers stage 3.
- **Stage 3**: return along route 5 to the hub -> route 8.
- **Stage 4**: return along route 8 to the hub -> route 12.
- **Stage 5**: return along route 12 to the hub -> route 10.
- **Stage 6**: return along route 10 to the hub -> route 7 (finish).

Each stage is therefore **"previous stage's end route reversed + next route
outbound"**. It is not a single `RouteConfig` and not `1_1 + 1_2`.

Evidence:

- Official rules v1: six fixed continuous paths; each starts at the previous
  endpoint, passes the central hub and ends at the next marker.
- Remote `route_1_3.yaml` comment says `spline0 + reverse(spline2)`. Its
  `route_1_3` entry has 269 points: the first 101 exactly match spline0 and
  the last 101 exactly match reversed spline2. The 67 intermediate points are
  generated by `splines_to_yaml.py`'s `connect_routes` using tangent extensions
  and a Bézier curve, and are not established as official geometry. The separate
  `route_road1` entry has 101 points. The previous 370-point statement counted
  both entries and must not be used as the stage-1 point count.
- Remote `/airsim_node/end_goal` for stage 1:
  `(545.56, 519.85, -30.21)` (NED).
- The remote `route_follower` flew stage 1 at about 10 m/s and logged gates;
  this is a runtime smoke test, not a scored run.

## OL1 scoring audit and remaining uncertainty

### OL1 seed 123 scoring-component audit

Read-only GDB and process-memory inspection of simulator 12.0.0.5
(SHA-256 `5231addfa25ddaa9e4473ea9ac40c9c0bc685174e69cd14bb49159f443b97800`)
found two route actors with 33 and 30 scoring components. The first road's
trigger order is component indices 32 down to 0; the second is 0 up to 29.
The native function `0x2fc8d80` checks the pending queue's first index,
removes the matching item and increments the internal Score. Hardware
watchpoints observed this increment at `0x2fc8fc4`. Thus 63 scoring components
are identified for this OL1 seed 123 route, subject to the stage and run
limitations below. Component root positions, quaternions and scales are saved
under `data/audits/ol1_seed123/`; their frame and trigger aperture still need
calibration before use in training.

The first probe started after the game had finished, and recorded the first
road's full 32→0 sequence. A second probe attached after Score had reached 13
in `State1`; it recorded the rest of the first road and all 30 second-road
indices. This second run entered `Finished` at Score 43, cause not established;
the simulation continued generating scoring callbacks after termination. The
observed value 63 therefore does **not** demonstrate 63 valid race points,
successful stage completion, or stage 2 transition. Controller used debug
pose and all-stop GDB affected timing. Raw logs and GDB commands are retained
with the component snapshots. No result is an official competition score.

A third diagnostic flight targeted 15 m/s and recorded the complete first-road
32→0 score sequence while in State1. It entered Finished at Score 33 near the
hub. The captured caller is a generic event dispatcher (`0x2fce60b`); the
failure cause and stage-2 transition remain unverified. Component coordinates
match the local Hermite spline model approximately: comparing reconstructed
stations against captured positions gives maximum residuals about 0.40 m on
road 1 and 0.23 m on road 3. The stationing formula is provisional and does
not establish trigger dimensions or the full coordinate contract.

### Audit observations (2026-11-06)

- Remote `route_follower/scripts/route_follower.py` publishes
  `/rmua/controller/events`; its `event()` docstring explicitly calls these
  controller diagnostics, not independent race scoring. Its gate events are
  computed from `chain.gates` by `task_state.step`. They cannot independently
  establish the official gate count or order.
- In a freshly launched OL1 seed 123, while the drone was stationary,
  `/airsim_node/custom_msgs` was absent from `rostopic list`; `rostopic type`
  returned unknown and an echo timed out. This does not rule out an event-only
  publisher appearing after a race trigger. No gate crossing was performed.
- `RouteGateConfigs` in the exported OL1 map lists indices 1–12 and references
  the 12 named route gate actors. It does not by itself establish the complete
  scoring detection-gate list.
- Runtime initial pose was approximately (0, 0, 0) NED and `end_goal` was
  (545.55995, 519.85475, -30.21286) NED. The simulator was stopped after
  inspection; the container remains running. Runtime log:
  `/tmp/codex_gate_audit_sim.log` on the remote host.
- A subsequent seed 123 diagnostic flight used `route_follower`, the partial
  vision gate list, recorded guides and `debug/pose_gt`. The controller reported
  reaching its 1449 m route end; a subsequent truth sample was approximately
  (544.07, 520.89, -32.31) NED while `end_goal` remained (545.56, 519.85,
  -30.21). This does not establish a stage transition or official success.
  Periodic ROS topic lists spanning the flight did not show `custom_msgs`;
  polling can miss short-lived publishers. Controller log is in container
  `/tmp/codex_gate_flight_controller.log` and topic samples in
  `/tmp/codex_topics_audit.log`. Both are diagnostic, not race scoring.

Next, establish the official scoring trigger source (including whether the
custom topic appears during gate crossings) and correlate it with route and
map geometry. Do not infer official events from controller diagnostics.

- The map UAsset contains only 12 objects named `*_Gate` (`1_1_Gate` ..
  `6_2_Gate`). These look like hub/route gates, not the full detection-gate set.
- Remote `gates_vision_1_3.yaml` has 10 gates, but it is a **vision-derived
  partial list**, not the official full gate table.
- The user's recollection of about 67 points before stage 2 has not been
  confirmed. A previous guess that 60–70 applies to the whole course was
  unsupported and should not guide the audit.
- A prior OL1 seed 123 runtime trace recorded 33 spline-segment enter events,
  indices 32 down to 0, on the first road. This suggests investigating a
  roughly 60–70-segment stage spanning two roads; the later scoring audit above
  establishes the relationship for this runtime. See upstream
  `experiments/segment_overlap_trace_20261104/README.md` and
  `segment_summary.json`.
- The exported OL1 `RouteConfigs` each specify `SegmentInterval=2100`.
  The sampled polylines for spline0 and spline2 in the remote `splines.txt`
  measure approximately 683.03 m and 624.45 m. If 2100 means 21 m and the
  engine rounds up, these suggest 33 and 30 segments respectively; the first
  agrees with the trace. This is only a calculation to test: spline length,
  interval units and rounding have not all been verified. The separate runtime
  audit above observes 63 scoring components, not a completed official run.
- `course.detection_gates_total: 12` in the current rules YAML is a legacy
  proxy validation value, not an established official detection-gate count;
  its consumers still assume it matches the proxy segment gate lists.
- Do not use 2, 10, or 12 as the official detection-gate count until the
  official runtime gate events / Trigger actors are audited.

## Factory logic

- Stage 1-3: no factory.
- 8-12: one factory before the hub.
- 12-10: one factory before the hub and one after the hub.
- 10-7: one factory before the hub and one after the hub.
- Exact entry/exit and reporting triggers are not confirmed. Keep this as a
  configurable state machine; do not hardcode a guessed sequence.

## Status of previous local results

The 1.47 km `1_1 + 2_1` route with two gates is a **proxy**. The reported
100% / 20.6 m/s stage-1 result is only a pipeline smoke test and is **invalid
for official stage 1**. The official route/gate model must be rebuilt from
the audited component data and a calibrated hub connection before official
validation. The opt-in local development environment is documented in
`stage1_environment.md`.

A new local BC+DAgger policy now completes the audited development environment
(63/63 components, 1474.431 m) on 320/320 held-out episodes at 21.99 m/s. That
validates the local training/environment pipeline only. The hub connector,
aperture, coordinate alignment and official stage-2 transition remain
unverified; do not treat local completion as an official score.
